MCP server · Playwright · self-hosted

Dê ao seu assistente de IA as mãos pra escrever, rodar e corrigir os próprios testes E2E.

tuxedo-qa é um servidor MCP + dashboard local que conecta na conversa que você já está tendo com a IA — sem pipeline de CI, sem infraestrutura compartilhada, sem segredo de teste vazando pra lugar nenhum.

O problema

Monitoramento sintético sempre exigiu escolher um extremo

SaaS de monitoramento

Cobertura pronta, mas você escreve e mantém o teste manualmente, credencial de teste mora num painel de terceiros, e a fatura chega todo mês.

Pipeline de CI próprio

Controle total, mas alguém precisa configurar runner, scheduler, storage de resultado, alerta — e ficar reescrevendo specs Playwright cada vez que a UI muda.

Você já está numa conversa com a IA descrevendo o que quer testar. Se ela puder escrever o Playwright, rodar, ler a falha e corrigir sozinha — e um humano só entra pra aprovar credencial e 2FA — o custo de manter uma suíte sintética cai pra perto de zero.

Como funciona

Da descrição ao teste agendado, numa conversa

O assistente de IA chama ferramentas MCP ao longo da conversa; o humano só entra pra aprovar credencial, 2FA, e ver o resultado no dashboard.

Dashboard local

A parte que nunca passa pela conversa com a IA

Uma instância, todos os projetos, um seletor pra trocar de contexto.

Monitor

Visão consolidada de todos os projetos registrados: contagem de testes, últimas execuções, o que está rodando agora.

Testes

Cria (via IA), roda e acompanha execução ao vivo — passos, log e status — com histórico de runs.

Credenciais

Cofre local onde o humano preenche valores pedidos via request_credential. O valor nunca aparece numa resposta MCP.

Proteção

Headers HTTP extras pra acessar ambientes de staging protegidos por senha ou token.

Status Page

Página pública opcional expondo um subconjunto de testes selecionados, num slug próprio.

Isolamento estrito

Um SQLite por projeto — não é uma convenção de query, é estrutural: uma conexão nunca alcança o dado de outro projeto.

Arquitetura

Local-first, containerizado, pronto pra crescer

Dois serviços Docker — leve na frente, pesado (browsers) isolado atrás — comunicando por rede interna.

app porta publicada

API REST, MCP Streamable HTTP, scheduler (~60s), hub de SSE, serve o build do dashboard. Sem dependência de browser — imagem leve oven/bun.

runner rede interna

Playwright + Chromium + Xvfb/x11vnc/websockify. Executa specs, faz inspect_page, e serve pair-debug via noVNC — proxied pelo app.

Bun TypeScript Hono Playwright React + Vite SQLite Docker MCP SDK noVNC
Quickstart

Do clone ao primeiro teste rodando

1. Clonar e instalar

git clone git@github.com:jonathan-ponciano/sts-tuxedo-qa.git
cd sts-tuxedo-qa && bun install

2. Buildar as imagens

O runner usa a imagem oficial do Playwright como base (já resolve as dependências de browser); o app builda a SPA num estágio e copia pro runtime final.

docker build -t tuxedo-runner -f apps/runner/Dockerfile .
docker build -t tuxedo-app -f apps/server/Dockerfile .
# ou, quando o plugin docker-compose estiver disponível:
docker compose -f docker/docker-compose.yml up --build

3. Subir os dois containers numa rede

docker network create tuxedo-net
docker run -d --name tuxedo-runner --network tuxedo-net -v $(pwd)/data:/data tuxedo-runner
docker run -d --name tuxedo-app --network tuxedo-net -p 3000:3000 \ -e RUNNER_BASE_URL=http://tuxedo-runner:4000 -v $(pwd)/data:/data tuxedo-app

4. Registrar um projeto

Abra http://localhost:3000, use o formulário "Novo projeto" no Monitor — ou registre via API:

curl -X POST localhost:3000/api/projects \ -H 'content-type: application/json' \ -d '{"slug":"meu-app","name":"Meu App"}'

5. Conectar seu assistente de IA

Aponte o cliente MCP (Claude Code, Claude Desktop, etc.) pro endpoint Streamable HTTP do projeto:

// mcp.json (ou config equivalente do seu cliente) { "mcpServers": { "tuxedo-qa": { "url": "http://localhost:3000/mcp/meu-app" } } }

A partir daí, é só descrever o fluxo pra IA: "monitora o login do meu app" → ela usa inspect_page, escreve o teste com create_test, roda com run_tests. Credencial pedida via request_credential você preenche no dashboard — nunca na conversa.
